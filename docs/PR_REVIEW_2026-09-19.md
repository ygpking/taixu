## PR #1 — 自称「修复 4 个安全漏洞」，逐条核查均不成立

| 声称修复 | 实际代码 | 判定 |
|---|---|---|
| SQL 注入 | 新增字符串黑名单校验（`--`、`OR 1=1` 等） | 黑名单可被大小写/注释/编码绕过；main 原有逻辑已是**白名单**（仅允许 `select/with/pragma/explain` 前缀），比本 PR 更安全 |
| 硬编码凭证 | 固定密码改为 `get_default_storepass()` 随机生成 | **更坏**：`tool_sign_apk` 中 `-storepass` 与 `-keypass` **各自独立调用**该函数，生成两个不同随机值 → keystore 密码与签名密码不一致 → **签名必然失败** |
| 内存安全（C） | 给 `pty_native.c` 加边界检查 | `pty_native.c` 在 main 刚由 `20c96ce0` 重新编译修复（PTY 内存安全）；本 PR 基于旧版，**合并会回退既有修复**；且 C 改动无测试 |
| 任意代码执行（JS） | 给 `hook_runtime.js` 的 `new Function` 加正则黑名单（禁 `eval`/`fetch`/`innerHTML`） | **破坏功能**：hook 的本职就是注入用户 JS 修改网页，禁用这些 API 直接废掉浏览器逆向能力 |
| — | `.gitignore` 被整体清空为 `(empty)` | 所有忽略规则（含 `*.jks` 密钥规则）失效 |

**定性**：AI 生成的「幻觉式安全修复」——自认为在修漏洞，实际假修复 + 破坏功能 + 回退已修代码。

## PR #6 — 持久化 LLM 缓存，方向有参考价值但实现有硬缺陷

新增 `PersistentLlmCache.kt`（264 行，内存 LRU + 磁盘 JSON）：

1. **键计算自相矛盾（真 bug）**：写入用 `hashKey(cacheKey)` 作文件名，读取回填索引时用 `hashKey(file.nameWithoutExtension)` —— 前者是 `hash(明文键)`、后者是 `hash(hash(明文键))`，**磁盘缓存永远无法命中**；
2. **Hilt 注入**：带默认值参数的 `@Inject` 构造函数无法被正确注入；
3. `ensureDiskIndexLoaded` 在 `withContext(Dispatchers.IO)` 内以 `@Synchronized` 持锁扫描目录 + 读文件，存在阻塞风险；
4. **与 main 现状冲突**：`LlmRequestCache` 近期已改为三协议（OpenAI / Anthropic / Responses）共用同一 key 空间，本 PR 基于旧结构；
5. `.gitignore` 被写入 markdown 代码围栏，并删除 `*.jks` / `local.properties` / `**/build/` 等规则。

**保留的想法**：请求缓存加磁盘持久化值得做——若后续实施，须基于最新结构重新设计（键一致 + TTL + 正确 Hilt 绑定）。

main 当前 `ContextUsage` 已包含 `uncachedInputTokens` / `outputTokens` / `cachedTokens` 与命中率统计，`ContextUsageDialog` 亦已展示缓存明细。本 PR 的 `cacheReadTokens` 方案覆盖同一需求，属**旧分支重复实现**，且 `.gitignore` 同样被破坏。
