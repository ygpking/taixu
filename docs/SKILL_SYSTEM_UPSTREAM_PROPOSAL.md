# TaiXu 技能系统增强提案：从「静态技能列表」到「可发现 · 可按需加载 · 能自我进化」

> **对比基线**
> - 上游主线：`wkbin/taixu` @ `f82a44f7`（Release v0.16.0，2026-09-20）
> - 本分支：`ygpking/taixu` @ `948e1c5c`
> - 核验方式：全部结论均以 `git show` / `git diff` / `git grep` 实际比对得出，逐条附证据，无推测。

---

## 一、这份文档在说什么

上游 v0.16.0 的技能体系，本质是**一份静态的技能列表**：用户在设置里建好技能，写消息时 `@` 一下，技能正文被塞进系统提示。

我们在此基础上补了三条链路，让技能从「用户手动喂」变成「模型能自己找、自己读、还能自己沉淀」：

| | 上游 v0.16.0 | 本分支 |
|---|---|---|
| 模型能否自己发现技能 | ❌ 无目录 | ✅ 系统提示内注入技能目录 |
| 模型能否按需拉取技能正文 | ❌ 无 `load_skill` 工具 | ✅ 有（精确命中 + 候选清单） |
| 会话结束能否自动沉淀技能 | ❌ 无此概念 | ✅ 技能进化顾问 |
| 含空格技能名 `@` 是否生效 | ❌ 手打时静默失效 | ✅ 整名匹配 |
| 自定义系统提示下技能是否可见 | ❌ 目录整体丢失 | ✅ 兜底注入 |

下面逐条展开。

---

## 二、新增能力（上游完全没有）

### 2.1 模型自主技能发现 + 按需加载

**上游现状**：技能正文只能靠 `@` 提及一次性塞进系统提示。模型没有「技能目录」，也没有「我要看看某个技能的详细说明」这个动作。

**证据**：
```
上游   load_skill 命中数: 0
本分支 load_skill 命中数: 11
```
```
上游   SkillSuggestion 命中数: 0
本分支 SkillSuggestion 命中数: 14
```

**本分支做法**：系统提示中注入技能目录（名称 + 用途 + 触发命令），模型据此判断当前任务该用哪个技能，再调用 `load_skill` 拉取完整正文。这样技能正文不必常驻提示（省 token），又能按需取用。

**为什么有价值**：技能数量一多，全量注入会把系统提示撑爆。目录 + 按需加载让技能数可以无上限扩展，而模型始终只看得到「摘要层」。

### 2.2 对话后技能进化（自我沉淀）

**上游现状**：`harness/skill/` 目录**为空** —— 没有 `SkillEvolutionAdvisor.kt`。

**本分支**：新增 276 行的 `SkillEvolutionAdvisor`。一次运行成功结束后，系统回顾本次做了什么，主动建议：

- 「你这套流程挺通用，要不要存成技能？」
- 「已有技能 X 的说明和实际操作对不上，要不要更新？」

建议以卡片形式出现在对话里，用户点一下就能落地成技能，或忽略。

**为什么有价值**：这是把「用户踩过的坑、摸索出的做法」自动固化成可复用资产的闭环。上游的技能只能靠用户手写，本分支让 AI 参与经验沉淀。

### 2.3 `load_skill` 的精确命中（避免选错技能）

**问题**：按需加载如果只做「包含」模糊匹配并静默取第一条，会出现 `load_skill("Git")` 却加载了「Git 敏捷工作流」的情况 —— 模型拿到的技能不是它想要的那个。

**本分支做法**（`ToolExecutor.kt`，精确优先 + 模糊兜底 + 多条返回候选）：
- 先按 name / id / 去斜杠 triggerCommand **精确匹配**
- 未命中才退回模糊匹配
- 模糊命中**多条时不猜**，返回候选清单让模型自己选

## 三、上游未修的缺陷（本分支已修）

### 3.1 🔴 含空格的技能名 `@` 时被截断（手打路径静默失效）

**问题**：上游解析 `@提及` 用的正则是：

```kotlin
// 上游 harness/.../MentionExtractor.kt:7（原文）
val regex = Regex("""@([^\s@,，:：\n]+)""")
```

它只认「连续的非空白字符」。用户手打 `@Git 敏捷工作流 帮我回退合并`，这段只会解析出 `Git`。技能名是「Git 敏捷工作流」，`Git` 匹配不上 → **技能静默失效**，界面上没有任何提示。

雪上加霜的是：UI 侧的高亮正则**支持**带空格的全名，所以界面上「Git 敏捷工作流」是被高亮的，用户以为识别成功了。

**影响范围**：内置 11 个技能中，**名字含空格的有 6 个**（逐条数过 `AgentSkill.kt`）：

| # | 技能名 |
|---|---|
| 1 | `Linux 沙箱运维专精` |
| 2 | `Git 敏捷工作流` |
| 3 | `Google Android 原生开发助手` |
| 4 | `Android 逆向与代码审计` |
| 5 | `Flutter 跨平台开发助手` |
| 6 | `CodeGraph 代码知识图谱` |

**上游状态**：**未修**（`parse` 至今只有一个参数、无 NFKC 归一、无邮箱保护）。

**本分支修法**：重写为「显式终止符 + 已知名单最长优先匹配」：
```kotlin
// 本分支 MentionExtractor.kt
private const val HARD_BOUNDARY =
    "\\s@,，:：;；!！?？。、()（）\\[\\]【】{}<>《》\"'“”‘’`|/\\\\"
```
配合已知技能名清单做最长优先匹配，`@Git 敏捷工作流-进化` 会命中更长的那个而不是 `Git` 或 `Git 敏捷工作流`。

> **如实说明**：从 `@` 菜单**点选**插入的是稳定 id（如 `@git_workflow`，不含空格），这条路径在上游本来也能命中。缺陷精确发生在**用户手打显示名**时 —— 而这恰恰是 UI 高亮让人以为可行的路径。

### 3.2 🔴 中文标点不断句

**问题**：上游正则不含 `。！？）` 等中文标点。用户写 `@CodeGraph。帮我看看`，句号被吃进名字变成 `codegraph。` → 失配。

**上游状态**：**未修**（终止符清单里没有中文标点）。

**本分支**：终止符清单统一包含中英文标点、各类括号、引号、命令分隔符。

### 3.3 🔴 全角输入失配

**问题**：中文输入法下容易打出全角 `＠` 或全角字母 `Ｇｉｔ`。上游不做归一化，直接失配。

**上游状态**：**未修**。

**本分支**：NFKC 归一化后再匹配。

### 3.4 🔴 已禁用的技能仍会被 `@` 注入正文

**问题**：用户在设置里**关掉**了某个技能，但选择逻辑不看启用开关：

```kotlin
// 上游 SystemPromptBuilder.kt:299-304（原文）
return allSkills.filter { skill ->
    val nameLower = skill.name.lowercase()
    val idLower = skill.id.lowercase()
    val cmdLower = skill.triggerCommand?.removePrefix("/")?.lowercase().orEmpty()
    nameLower in mentionedNames || idLower in mentionedNames || (cmdLower.isNotEmpty() && cmdLower in mentionedNames)
}
```

没有 `isEnabled` 判断 → 用户以为关掉了，`@` 一下正文照样被注入。这还与 `load_skill`（走 `activeSkills`，只取启用的）**口径打架**：同一个技能，按需加载拿不到，`@` 却能注入。

**上游状态**：**未修**。

**本分支**：加 `isEnabled` 过滤 + 归一化比较，与 `load_skill` 门禁对齐。

### 3.5 🔴 自定义系统提示下，整份技能目录丢失

**问题**：技能目录靠系统提示模板里的 `{{ACTIVE_SKILLS}}` 占位符嵌入。内置模板 `core.md` 有这个占位符所以没问题；但用户一旦启用「自定义系统提示」，自定义内容里通常**不会写这个占位符** —— 整份技能目录凭空消失，模型完全看不见任何技能。

**上游状态**：**未修**（上游 `resolceSkillCatalogFallback` 之类命中数为 0，只有占位符注入一条路）。

**证据**：
```
上游   resolveSkillCatalogFallback/SkillCatalogFallback 命中数: 0
本分支 resolveSkillCatalogFallback/SkillCatalogFallback 命中数: 2
```

**本分支**：新增兜底逻辑 —— 检测到自定义提示且未包含占位符时，把技能目录作为独立分节补注入。**不改动用户的提示内容**，只是在缺失时补上目录。

### 3.6 🟡 UI 与后端「两套标准」

**问题**：负责高亮的 UI 正则和负责解析的后端正则各写各的。上游 UI 支持带空格全名高亮，后端却在空格处截断 —— 制造出「界面高亮了、后端没解析出来」的错觉陷阱（3.1 的观感来源）。

**上游状态**：**未修**（UI 正则内联写死，无共享常量）。

**本分支**：抽出共享常量 `MENTION_HARD_BOUNDARY `，两侧引用同一份终止符定义。

### 3.7 🟡 技能正文注入无长度护栏

**问题**：技能正文直接拼接进系统提示，没有上限。巨型技能会把系统提示顶到上下文上限，然后**从尾部开始砍** —— 砍掉的可能是 recall、workspace 等必备段落。

**上游状态**：**未修**。

**本分支**：单技能正文 8000 字符、累计 24000 字符护栏，超限时截断并标注。

### 3.8 🟡 目录条数静默硬截断

**问题**：目录有 `MAX_CATALOG_ENTRIES = 24` 硬上限，超出部分**静默丢弃** —— 用户建了 25 个技能，第 25 个模型完全看不见，且没有任何提示。

**上游状态**：**未修**。

**本分支**：截断时显式提示「还有 N 个技能未列出」，让模型知道存在更多。

## 四、本分支内部的自我修正（补充说明）

以下几项严格说不是「上游对比」，而是本分支先做、再发现并修正的问题，列出以保证提案完整：

| # | 问题 | 修法 |
|---|---|---|
| 1 | `MIN_TOOL_CALLS = 3` 是**死常量**（定义了从不使用），寒暄单轮也触发技能分析 → 白烧 token | 补上工具调用计数据，真正按门槛触发 |
| 2 | 冷却判定发生在快照**之前**，空跑也会占用 30 分钟冷却窗口 | 判定前移；冷却表按会话清理（防内存泄漏） |
| 3 | 技能建议**无幂等**：重复点击 / 重启后卡片复活 → 重复建技能 | 以建议 id 为种子做幂等闸门，失败回滚允许重试 |
| 4 | `addCustom` 失败被 `runCatching` **静默吞掉**，卡片照样消失，用户以为建好了 | 失败接入项目既有 `notice` 通道 → Toast 可见 + 保留卡片 |
| 5 | 「另存为新」与原名同名 → `load_skill` 命中不确定 | 重名自动追加 `-2` / `-3` 后缀 |

> 这些测试文件对应的功能，本分支**要么上游已实现而我们未跟进、要么我们的实现路径不同**。这是一处**需要正视的差距**，不应被解读为「我们测试更少但更精」——本分支在技能线新增了 5 个测试文件，但在其他领域确实落后于上游。合并时需评估这 21 个测试覆盖的功能是否已在本分支具备。

## 六、影响面与取舍

**对上游的价值**：
1. 技能体系从「静态列表」升级为「可发现 + 可按需加载 + 能自我沉淀」，技能数量不再受系统提示长度限制。
2. 修复 6 个内置技能手打 `@` 静默失效的问题（用户可感知的功能性缺陷）。
3. 修复自定义系统提示下技能目录整体丢失的问题。

**需要上游决策的点**：
1. **邮箱行为变更**：是否接受「邮箱不再被当作提及」？（第五节说明）
2. **技能进化是否默认开启**：该链路会调用一次额外的模型请求做回顾分析，涉及 token 成本。本分支已加工具调用门槛与 30 分钟冷却来控制频率，但上游若认为成本敏感，可考虑默认关闭 + 设置项开启。

**兼容性**：
- `MentionExtractor.parse` 新增**可选参数** `knownNames`，默认值保持旧签名可用，不破坏现有调用。
- 自定义系统提示内容**不做任何修改**，仅在缺失占位符时补注入目录。
- 内置 `core.md`（含占位符）路径行为不变，不重复注入。

## 七、结论

本分支在技能系统上完成的是**从 0 到 1 的两条新链路**（自主发现、自我进化），外加**修复 8 处静默失效缺陷**。

其中 3.1、3.5 两条是用户可感知的功能性缺陷（技能不生效 / 技能看不见），建议优先采纳；其余为健壮性与体验改进。

所有结论均有 `git show` / `git grep` 实测证据支撑，欢迎按证据复核。
